# Threat Model

## Assets

- User privacy and personal data.
- Workspace files.
- Credentials and secrets.
- Audit integrity.
- Policy and approval integrity.
- Model output quality.

## Threats and Mitigations

| Threat | Mitigation |
|---|---|
| News-current fact fabrication or citation laundering | News Intelligence policy requires current/live claims, timelines, source comparisons, and briefs to cite only returned sources with source ID/URL, provider, retrieved_at, freshness window, and publication/event dates when available. Outputs must report coverage limitations, conflicts, failed/blocked sources, and separate facts from inference; fabricated headlines, dates, URLs, and citations are forbidden. The manifest now declares planned news workflows as disabled placeholders, so future runtime work must deliberately add ToolBroker-routed implementations and tests before execution. |
| News provider bypass, surprise paid API use, or over-retention | News provider strategy is free-first and cache-first, with paid providers skipped unless explicitly configured and allowed. Login/paywall/CAPTCHA/anti-bot bypass is forbidden; blocked sources return unavailable/setup guidance. Search/news history, full article bodies, translations, and source text are not stored by default; binary/downloaded article files are HIGH or disabled; provider choices and skipped reasons must be audited in future runtime work. Current `NEWS_*` defaults and provider-policy tests keep paid APIs disabled, search history off, article-body storage off by default, and all `news.*` manifest entries default-disabled/planned. |
| Native skill docs generator becomes a trust or execution side channel | Native skill docs generation is metadata-only and dry-run by default for command-triggered changes. It reads manifests, command registry metadata, profile/compatibility/provenance/lock/test/dogfood/docs metadata, preserves manual notes outside marked generated sections, reports missing docs, includes deprecated/blocked skills, and copies maturity from manifests without upgrading it. It does not execute skills, external scripts, package managers, providers, connectors, plugin runtimes, permissions, or memory writes. |
| Platform bridge bypass or native OS side door | Cross-platform architecture requires platform bridges to be optional/lazy adapters, never direct workflow executors. Platform Capability Registry v1 is metadata-only and keeps future capabilities disabled and non-executable; unknown platforms/capabilities return unsupported records. Platform bridge base interfaces now provide `NullPlatformBridge` as a fail-closed default, side-effect-free `prepare_action()`, blocked direct `execute_action()` behavior, lazy registry loading, metadata-only health checks, and audit correlation fields for future brokered results. Read-only `platform.*` doctor/status/capability commands are SAFE ToolBroker/PolicyEngine/AuditLogger metadata tools and do not execute bridge actions. macOS/iOS/Windows/web bridge stubs now lazy-load through the bridge registry and inherit fail-closed behavior: direct execution is blocked, broker-context execution returns `requires_setup`, health checks read no personal data, and stubs import no native OS frameworks. The cross-platform release gate adds future macOS/iOS/Windows/app frontend build guides that require manifest mapping, ToolBroker routing, PolicyEngine/PermissionManager/ApprovalManager/AuditLogger gates, tests, command registry updates, conservative maturity updates, startup-overhead checks, unsupported behavior handling, and explicit approval before forbidden platform behavior. Future platform actions must be capability-manifest declared, routed through ToolBroker, evaluated by PolicyEngine, checked by PermissionManager, approval-gated by ApprovalManager for HIGH/CRITICAL risk, audited by AuditLogger, and tested for unsupported/setup-required behavior. |
| Platform startup overhead or native dependency creep | The performance overhead policy forbids native framework imports, heavy bridge imports, network calls, subprocesses, personal file scans, permission prompts, app bridge server startup, polling loops, and background workers during core startup. Platform Capability Registry v1 import tests verify the registry does not import native macOS/iOS/Windows modules. Platform-aware config/detection/path scaffolding reads only `sys.platform` plus explicit env metadata, keeps all bridge flags disabled/lazy by default, computes project-local paths without home-directory scans or directory creation, and returns `unknown`/setup guidance on detection failures. Platform doctor command tests verify command imports/outputs do not load native modules, request permissions, start app bridge servers, or execute platform actions. Bridge stub tests verify default registry registration does not import stub bridge modules and stub imports do not pull native frameworks. The cross-platform release gate import smoke confirmed `smart_agent` startup does not load platform stub bridge modules or checked native/heavy platform modules. Future platform release gates must include broader import-graph and startup side-effect checks. |
| App frontend approval confusion | Future app bridges may display status, pending actions, setup hints, and redacted audit summaries only. App Bridge v1 is contract/schema-only: disabled by default, localhost/IPC only, remote access unsupported, pairing required for sensitive surfaces, no server startup during import, and no native frontend implementation. Validation denies unpaired sensitive requests, ApprovalManager bypass attempts, missing audit correlation, personal-data status payloads, and CRITICAL approvals without exact preview, per-action approval, and no-reuse guarantees. |
| Tracker inconsistency or dense history causing unsafe release assumptions | Keep detailed trackers as source-of-truth records, add dashboard/index/maintenance/archive/consistency layers, prefer small anchored edits, preserve historical evidence through archive links, report disagreements instead of guessing, and update `docs/TRACKER_CONSISTENCY_REPORT.md` during release gates. |
| Release hardening overclaims readiness | Release Hardening Loop v2 records exact test/validation results, dirty-tree state, live/manual validation gaps, security scan caveats, release blockers, and a YELLOW readiness score. Local tests and mocked evals are not treated as proof of live provider readiness, generated local artifacts are classified separately from source changes in `docs/release/GENERATED_ARTIFACT_HYGIENE.md`, and future feature maturity must remain conservative until release-gate evidence supports promotion. |
| Model hallucination | Keep harness thin; model final answers are not proof of action; actions must have tool results. |
| Prompt tracking drift | Keep a prompt ledger, ordered prompt queue, prompt audit, prompt record directories, and validation tests; AGENTS requires prompt status updates and final reports must include `prompt_id` plus `next_prompt_id`. |
| Prompt completion evidence spoofing or staleness | Prompt evidence is heuristic and treated as review data, not proof by itself. The tracker classifies evidence status, requires mark-complete test/docs fields, limits one active prompt, requires failed reasons, and reports recovery plans without auto-running prompts. |
| Golden eval overreach or stale quality claims | Golden evals default to safe categories, keep personal-data evals skipped, keep live LM Studio/provider checks opt-in, execute tool checks through `ToolBroker`, write pass/fail/skipped reasons with scorecards, and must not be treated as proof of live user readiness without a recorded live run. |
| Model-router benchmark overclaiming quality | Model-router and prompt-quality evals are fixture-backed by default, do not send prompts to LM Studio unless live mode is explicitly requested, compare route/tool/policy expectations to actual behavior, treat prompt-injection fixture text as untrusted data, and do not execute personal-data or send/write tools. |
| Prompt pack instruction smuggling | Prompt packs are parsed as SDLC data only; importer rejects `execute_all`, writes split files to `prompts/queued/`, preserves prompt body text including embedded delimiter examples without executing it, and `prompts next` skips blocked approval-gated prompts. |
| PromptOps autopilot overreach | `work run-next` is disabled by default; `work autopilot` requires `--safe-only`, only considers safe risk levels and allowlisted categories, stops at approval gates, and never treats imported prompt text as trusted policy instructions. |
| Overnight self-improvement overreach | Overnight work is constrained by `docs/SELF_IMPROVEMENT_OVERNIGHT_RUNBOOK.md`: allowed work is docs/tests/diagnostics/evals/tracking and low-risk refactors only; forbidden work includes personal-data connectors, sends, calendar/contact writes, policy weakening, approval bypass, audit disabling, package installs, external scripts, full disk access, persistence/background agents, unapproved commits, and unplanned network. `improve overnight-plan` is plan-only and excludes HIGH/CRITICAL/personal-data candidates. |
| Command catalog drift | `docs/COMMAND_REGISTRY.md` and `docs/COMMAND_TEST_MATRIX.md` are generated from command metadata and validated by `commands validate` plus tests; AGENTS requires updates whenever CLI commands are added, changed, renamed, deprecated, or removed. |
| Secret/config doctor leakage | `secrets doctor/status`, provider connector status commands, `gmail doctor/scopes`, and `telegram doctor/status` report redacted presence/config metadata only, make no provider API calls, do not read Gmail/Telegram data, warn on tracked `.env`, repo-local Gmail token paths, broad Gmail scopes, and missing Telegram chat allowlists/defaults, do not promote paid providers into defaults, and keep Gmail/Telegram sends disabled and CRITICAL. |
| Apple ecosystem overreach | Apple ecosystem connectors must be selected-scope, disabled by default, brokered, audited, and permissioned. Calendar/Reminders should use EventKit or a reviewed native bridge, Contacts should use selected records and fields, Mail/Gmail should stay metadata/read-selected/draft-first, and future sends/writes remain HIGH or CRITICAL with Action Center approval. |
| Consumer Messages/iMessage unsafe access | The project does not have a safe general consumer iMessage inbox/send API. Strategy docs reject private Messages database scraping, broad Full Disk Access, broad history reads, AppleScript/Accessibility auto-send, hidden polling, and contact harvesting. V1 remains manual selected text, workspace context, draft, save, and copy handoff only. |

Message reads are HIGH, message sends are CRITICAL with exact per-action approval and no reuse, bulk sending is FORBIDDEN in v1, and unsafe platform gaps must return clear limitations. |
| Messaging abstraction send bypass | Message Channel Abstraction v1 is draft/preview/validation first. Channel metadata is brokered and audited, no direct or silent `messaging.send` capability/tool exists, generic send execution remains unregistered, send request models default to CRITICAL with exact preview and no approval reuse, macOS send execution is a separate disabled-by-default adapter, and validators reject unknown channels, missing recipients, empty bodies, group/bulk recipients, and unsupported attachments before any adapter can run. |
| Message send approval confusion or reuse | Message Safety Policy v1 creates CRITICAL Action Center items from existing local `MessageDraft` records only. Exact local previews include channel, recipient, full body, attachments, source context, rollback impossibility, explicit per-action approval, allowlist status, and rate-limit status. Draft edits invalidate pending/approved send actions, approval reuse is disabled, untrusted content cannot create a send action without explicit user request, non-interactive execution has no send path, and audit/export records redact message bodies and recipients. |
| iOS compose handoff confused with message delivery | iOS compose bridge v1 writes expiring local payloads for a future companion app or compose UI only. Payload creation and result recording go through `ToolBroker` and `AuditLogger`, approved-action payloads must match the Action Center preview fingerprint, compose-only mode still requires the user to review native compose UI and tap Send, expired payloads cannot record `sent` or `queued`, and no silent-send tool, app bridge, Messages database read, or background delivery path exists. |
| Lead response automation overreach | Lead Response Drafting v1 is a mock/local workflow, not permission to read real providers or auto-send. Lead text remains `UNTRUSTED_MESSAGE` data, selected full-message reads are HIGH and disabled by default, classification and summarization create no actions, drafts are editable `MessageDraft` records with source and assumptions, follow-up tasks become pending Action Center records only, and meeting suggestions do not read calendars or create events. Approved Lead Response Send v1 creates only CRITICAL exact-preview Action Center proposals, rejects bulk recipients/attachments, invalidates approval after draft edits, denies approval reuse, routes only through existing channel gates, returns fallback options for unsupported channels, and writes no lead content to memory by default. Auto-response remains deferred until a future explicit policy and release gate. |
| Lead source adapter privilege creep | Future Gmail, Telegram, Apple Messages for Business, personal iMessage manual, web-form, or CRM adapters must stay selected-scope and disabled by default. Token/config presence must not grant inbox reads or sends, provider adapters must go through ToolBroker/PolicyEngine/ApprovalManager/AuditLogger, and private Messages database scraping, broad Full Disk Access, hidden polling, bulk ingestion, CRM sync, memory storage, and auto-response remain out of scope until separate reviewed prompts. |
| Apple Messages for Business provider stub mistaken for live provider readiness | The v1 Apple Business provider is mock/local only. `apple-business doctor/status` inspect config metadata without provider API calls, `mock-inbound` stores local `UNTRUSTED_MESSAGE` Lead Inbox records, and `draft-response` creates local `MessageDraft` records only. No credentials are required, no live webhook is polled, no send action is created, no send executes, and future provider sends remain disabled, CRITICAL, exact-preview, per-action, and no-reuse. |
| Manual QA accidentally running risky commands | `commands qa-run` prints SAFE/LOW active command examples only and does not execute them in v1. HIGH/CRITICAL, personal-data, write/send, blocked, planned, stubbed, and legacy commands remain manual checklist items with approval gates and explicit QA notes. |

| Forum dogfood/eval and release-gate overclaiming | Forum dogfood/eval v1 plus the Forum Intelligence release gate are validation harnesses, not permission to broaden forum access. Forum suite/eval text is untrusted review data and cannot authorize scraping, login/cookie/session automation, CAPTCHA/anti-bot bypass, paid provider default use, forum-content training, memory writes, posting/commenting/voting/DMs, or policy/audit bypass. |
| Messaging dogfood mistaken for live-send validation | Messaging dogfood suites are local QA recipes, not permission to send. Planning commands read only suite/session metadata and feature-maturity notes; they do not run suites, access personal data, grant approvals, send messages, or change policy. |
| Product quality dashboard leaks raw QA evidence | The quality dashboard reads local metadata only, redacts feedback and bug text, avoids raw full session output and personal connector contents, performs no tool execution, grants no approvals, writes no memory, and prioritizes P0/P1 bugs without treating bug text as trusted instructions. |
| Session logging captures sensitive output | Session logs are separate from AuditLogger, redacted by default, ignored by git, and never written to memory automatically. The recorder does not collect environment variables and does not bypass ToolBroker or approval gates; `session run` only delegates to existing `smart_agent.py` commands. |
| Feedback capture stores sensitive or policy-changing text | Feedback records are redacted before storage, written only to session-local `feedback.jsonl`, included in show/replay/export as review evidence, and audited. Feedback text is never treated as approval, permission grant, policy change, tool request, send instruction, or memory content. Unsafe feedback raises severity instead of executing remediation automatically. |
| Session review turns logs into unsafe or leaky bug reports | Session review reads redacted session previews and feedback only, writes local redacted review/bug artifacts, does not send data externally, does not access personal connectors, does not write memory, and does not automatically fix bugs. Policy/ToolBroker/PolicyEngine/Approval/Audit bypass or personal-data leak signals are classified as P0 for human triage. |
| External native-skill supply-chain attack | Native Skills Program intake treats third-party skill text, marketplace pages, repositories, and examples as untrusted data. Intake does not install or run external code, opaque binaries, package scripts, browser extensions, or setup commands. Useful behavior must be re-specified as local project-owned workflows. |
| Native skill shadowing or precedence confusion | Native skill roots are explicit metadata records with deterministic precedence. Workspace, personal, reconstructed, and experimental roots are untrusted candidate sources; experimental roots are disabled by default. The precedence resolver reports duplicate skill IDs, winning candidates, shadowed candidates, and diagnostics, and untrusted roots cannot silently shadow trusted native/project skills by default. Root scans read `SKILL.md` and manifest files as `UNTRUSTED_DOCUMENT` and never execute scripts or import code. |
| Native skill dependency-gate escalation | Native skill manifests must declare dependency needs before use. Dependency gating is intentionally passive: env checks report presence with redacted values, config/binary/file/platform/capability/Python/model-feature checks return setup status only, and checks do not install packages, execute scripts, import skill modules, call providers, call connectors, request permissions, or scan personal files. | Silent native skill update or provenance drift | Native skill provenance records track source type/path/URL, review status, trust status, license, hashes, pin metadata, known risks, and caveats.
